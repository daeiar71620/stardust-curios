# Mixed native-v9 campaign validation

This suite supplements the isolated action matrices with continuous, mixed-action
campaigns. It uses only the explicitly supplied trusted public Python source and
synthetic in-memory games. It never opens a game save, database, observation file,
account, or network connection and writes no generated fixture state to disk.

## Scope and reproducibility

- `tests/campaign-oracle.py` selects actions from public observations only. It
  streams a start record, one full expected record per command, and a final
  coverage summary. It does not accumulate whole trajectories in memory
- `tests/campaign.test.mjs` runs the same commands against `executeNative`, with
  native seeded initialization also compared against Python
- Eight unmodified synthetic new games start with the normal 260 credits, run
  through the full first week, explicitly continue, and close day 14 (day 15 is
  the final public day)
- Twelve additional games are explicitly endowed with 12,000 synthetic credits
  at initialization. Four close day 35 and eight close day 21. Initial financing
  is the only state patch: every item, repair, collection, replacement, purchase,
  sale, facility, day transition, and later balance is command-generated
- Fixed seeds include 0, 1, 42, the maximum safe JavaScript integer, and a 129-bit
  seed passed as an exact decimal string/BigInt. No seed selection or action
  selection inspects hidden valuations, exact buyer budgets, RNG, or sealed cargo
- The fresh normal-start policy is a public-information trading policy; endowed
  policy variants additionally collect, repair, replace, upgrade, and alternate
  bargaining outcomes. They are test policies, not a claimed optimal strategy

Run from this package with Node 24 and Python 3:

```sh
STARDUST_ENGINE_SOURCE=/path/to/trusted/engine.py \
  node --experimental-strip-types --test tests/campaign.test.mjs

# Optional source-only coverage inspection; prints counts, never fixture states:
PYTHONDONTWRITEBYTECODE=1 python3 tests/campaign-oracle.py \
  --engine /path/to/trusted/engine.py --summary-only
```

The test is automatically included by the existing `tests/*.test.mjs` package
test glob. Streaming uses a backpressured process pipe and incremental UTF-8 line
decoder rather than `execSync`, whole-output capture, or an unbounded event queue;
no generated save/fixture JSON is retained.

## What is compared

For every successful or rejected command:

1. The complete private state, including all canonical CPython RNG state entries,
   sealed cargo, hidden buyer budgets, ordered histories, event snapshots, item
   locks, collection positions, counters, and provenance fields
2. All 39 public top-level fields and their complete nested contents. Both the
   direct projection and the dispatch response are compared
3. The exact Python error message for failed commands. Input state and RNG must
   stay unchanged; successful commands advance exactly one revision
4. A JSON serialization/rehydration round trip before the next observation and
   action. This occurs in memory, with no storage or API equivalence implied
5. `status`, `market`, `codex`, and `visitors` after every command, plus `inspect`
   for available inventory/cabinet items and a rejected inspection for unopened
   boxes. Every probe is repeated twice on the same state
6. When a bargain is pending, repeated `preview-offer` probes at the counter,
   just above the counter, just below the initial price, and the initial price.
   Python independently supplies the valid forecast or exact error

Read-command results are compared with the exact corresponding slices of the
independently generated Python public observation. For every read, the complete
returned state and caller input must be unchanged, and `mutated` must be false.
Reads do not advance revision, random state, energy, buyer capacity, or history.

Additional invariants assert that opening, pricing, collecting, replacing,
upgrading, accepting, and declining consume no random numbers. Explicit
continuation preserves inventory, collection, crates, facilities, and statistics,
advances from the day-7 pause to day 8, and does not charge maintenance again.

## Result and limitations

Verified on 2026-10-06 UTC with Node 24.19.0 and Python 3.12.14:

- All 20 campaigns and all 11,303 command comparisons passed
- 143,838 read calls passed, including 9,702 expected read errors; every applicable
  read was executed twice on each checked state
- 145,459 full direct/read projection comparisons passed. Successful mutation
  responses and their command-result payloads were also compared separately
- Complete private states/RNG, immutable caller inputs, exact error messages,
  JSON rehydration, one-revision commits, no-reroll locks, and read invariance
  passed throughout
- No semantic discrepancy was found in these trajectories
- The final streaming run completed in 641 seconds. The matrix is fixed and
  backpressured, but deliberately CPU-heavy; it is a substantial regression gate
- Package TypeScript checking, JavaScript syntax checking, and Python AST parsing
  also passed. Other existing suites were not rerun by this campaign worker

This is a bounded deterministic differential suite, not a proof of equivalence
for all states or action sequences. The initially endowed games are labelled
synthetic and do not claim to be reachable from an unmodified new game. The
normal-start runs reach a missed first-week result but do not lose to maintenance
in this fixed matrix; separate day-action fixtures cover bankruptcy boundaries.

The tested envelope is native fresh-v9 state with null import provenance and v9
trade rules. Legacy imports and old trade rules remain unsupported. The known
arbitrary-reference `Math.log2` portability limitation is not resolved by these
lawful campaign tests. No Worker deployment, D1 persistence/concurrency, HTTP/MCP
authorization, real save, migration, browser UI, or production outcome is tested
by this suite.
